### 我自己错了一次,已改

第一版 `e1db4f8d` 按 `batch × prompt vs 池子` 的算术把上限定成 64,并把算术写进了 spec 注释。
**被数据否掉**:batch 32 在 22 倍余量下照样抢占 44 次,而且 44 次全挤在 **11:40:18–11:40:45
一个 27 秒窗口**里。所以耗尽池子的不是 batch 的静态占用,是**在飞的 store 攒住块的瞬时积压**

另一个印证:**qwen3.8-27b 在默认 batch 下就是零抢占**,parity 直接过。所以上限必须按模型给,
不能设成全局默认——这条本来是判断,现在有数了。

## 三、代码(全部在 `tests/e2e_mm/`,生产代码零改动)

1. **`ModelSpec.mme_max_num_seqs` / `mme_gpu_memory_utilization`**,只作用于 parity 两侧引擎。
   刻意**不复用** `gpu_memory_utilization`(那个字段给合成套件用):复用会把已录的 13 份
   在 0.6 下跑出来的报告静默改形。不设时保持 0.6 和 vLLM 默认 batch。
2. **零抢占前置校验**。跑完读 `vllm:num_preemptions`(两遍各采一次),写进报告的
   `preemption` 块。非零则退 **3**,`certify.require_valid_parity_run` **拒发证书**——
   一次抢占的跑测的是上游缺陷,盖 NOT_SUPPORTED 等于指错人。
   `disable_log_stats=False` 是这条校验的全部支点(离线 `LLM` 默认关统计,计数器会恒为 0);
   已用 T0.11 近期通过的事实反证计数器在离线路径上确实工作。
3. **旧报告按"没人看过"处理**,不拒收,但证书上 `parity.preemption_check` 明写
   `not measured`,不假装测过零。
4. **`PREEMPTION_AVOIDED_NOT_COVERED`**:shaped 模型的证书声明放弃"池压力下的命中路径"这一档,
   并写明 **T0.11 虽然证明发生了抢占,但它的判据是被抢占那批自己的输出,没人回读那些请求
   存进去的东西,所以它对这个故障类是盲的**——这解释了为什么套件一直没抓到。
5. `IN_PROCESS_NOT_COVERED` 改写为"按决定不在范围内",不再是"只是没测"。
6. **`test_preemption_precondition.py`,42 条 CPU 单测**。副作用:`pytest .` 收集范围变大,
   证书里 `suite.tests` 从 ~46 涨到 86~88,不是回归。

## 五、跑歪了一个对照,结论仍然有用

为 phi4 跑了纯 vLLM 对照(batch 8 vs 64,全程无 LMCache):**174 处原文差异 → 解析后 0 翻转**。

**但这条量错了轴。** parity 门比的是 pass1(现算)vs pass2(加载),同一 batch 形状;
变量是"算出来的还是取出来的",不是 batch 形状。套件现在给 glm / kimi / qwen2-vl 用的对照
是同一个错轴。

**对得上的零假设**:同一引擎、同一 batch、**开 vLLM 自己的 prefix caching**,同样题目跑两遍,
第二遍命中 vLLM 内部前缀缓存,全程不碰 LMCache。它把"从缓存供数"这件事本身的翻转概率单独量出来
——命中后只对尾巴做 prefill,注意力核的 tile 形状和规约顺序变了,正是让 LMCache pass2 变化的
同一个机制。

已知的界限:vLLM 前缀缓存回的是**显存里逐位相同**的 KV,LMCache 要走 host 一圈。
所以这个对照是**合法地板的下界**;LMCache 高出它的部分才是需要论证的东西。

## 六、未闭合:预算是标定出来的还是调出来的

审了 16 个 spec 的 `mme_max_flip_fraction`:

| 模型 | 预算 | 依据 |
|---|---|---|
| glm-4.6v-flash | 1.50% | ✅ 实测地板 5.10%,预算远低于地板 |
| kimi-vl-a3b | 1.00% | ✅ 实测 0.46% |
| qwen2-vl-2b | 1.00% | ✅ |
| **qwen2.5-vl-3b** | **1.50%** | ❌ **无任何对照** |
| **qwen3.8-27b** | **1.00%** | ❌ **无对照**,靠同族继承 |
| qwen3.6-27b | 1.00% | ⚠️ 对照只有 0.084%,放宽靠论证(命中**恢复** GDN state page) |
| 其余 10 个 | 0.50% | 默认值,未标定 |

**5 个放宽里 2 个没有测量支撑,1 个的测量反而说明不该放宽。** 这正是"逐个调到全绿"的失效模式。

建议(**尚未实施**):统一的应该是**判据**不是数字。两个泊松计数落在同样题目上,对照 c、
LMCache f,要求 f 不显著大于 c,**α 全模型统一**。套件里已有先例:方向门 `flip_asymmetry_p`
就是统一 α=0.01。分两步走:先给 16 个模型各跑一次前缀缓存对照,把数记进 spec **但先不接进门**,
看完 16 个数再定判据形式——否则可能一次把现有的绿掀翻(若 phi4 的对照真是 0,它的 10 个翻转
按新判据不该过)。

## 七、`p1 vs plain vLLM ≈ 0` 是对照不是结果

用户问为什么这一列全 0 而 pass2 那列 6~24。原因:**pass1 是 miss 路径,LMCache 只写不读**,
没有任何东西被喂回计算,引擎配置和 plain vLLM 逐项相同(`engine_kwargs` 共用),
所以那一遍算的就是 plain vLLM 算的东西。它非零就说明两个引擎没配平,pass2 那列会没法解读
(mistral 的 5 是全表唯一非零,已保留)。

**但 0 不等于逐字节相同**,这点 PR 文本必须写准:

| 模型 | 原文 p1≠base | 原文 p2≠p1 | 结论翻转 p1/base | 结论翻转 p2/p1 |
|---|---|---|---|---|
| gemma-3-4b | 104 | 137 | 0 | 0 |
| phi4-mm | 126 | 239 | 0 | 10 |
| internvl3.5-2b | 35 | 302 | 1 | 6 |
| qwen2.5-vl-3b | 0 | 40 | 0 | 24 |
| deepseek-ocr | 1 | 137 | 0 | 11 |
| kimi-vl-a3b | 0 | 50 | 0 | 13 |

gemma-3-4b 104 处、phi4 126 处原文有差而结论一个没动;那是引擎自己的跑间不确定性
(baseline 在独立进程,请求进批组合不同)。审阅者自己复现看见字节差会以为出了问题。

**pass2 那列混着两个成分且分不开**:KV 走了 host 一圈 + 计算形状变了。这与第五、六节是同一个洞。

## 十、操作教训

- **`grep -c preempt` 会把报告 JSON 里的 `preemption` 键数进去**。判断有没有抢占要读报告的
  `preemption.total`,不要数日志行。
- **`setsid` 起的后台跑会脱离 harness 进程树**,工具会立刻报 "completed exit 0" 而活还在跑。
  要么别用 setsid,要么另起一个 waiter 轮询真实 pid。
- 停这类跑一律 `kill -TERM -<pgid>` 按组杀(`benchmark_parity` 会拉起忽略 SIGTERM 的 MP server
  子进程),再核 `nvidia-smi` 归零。
- **写 `records/` 下的新文件不会弄脏工作树**(`.git/info/exclude:19` 忽略 `records/`,
  而 `git_dirty` 用 `git status --porcelain` 不显示被忽略文件),所以 certify 在飞时可以先写记录,
  但**不能提交**——提交会移动 HEAD,`commit_at_start != commit_at_finish` 直接盖 `stable: false`。
