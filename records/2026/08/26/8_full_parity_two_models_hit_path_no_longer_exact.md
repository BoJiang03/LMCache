## 结论先写

1. **LMCache 的 hit 路径在 vLLM 0.27.1 上有一个可复现的确定性偏差。**
   qwen2-vl-2b 全量 MME 跑三次,pass2 相对 pass1 翻的题:19 / 19 / 18,
   **三跑交集 18、并集 20**,两两 jaccard 0.900 / 0.947 / 0.947。
   固定的那 18 题是:

   ```
   241 299 329 352 392 396 449 465 531 741 781 823 949 996 1072 1482 1576 1618
   ```

   门的预算是 11.87(0.005 × 2374)。**单是确定性的那 18 题就已经超了** ——
   所以这个红不是阈值标定问题。

2. **存路径是干净的。** pass1 与 plain vLLM 的 baseline:0 flip,14 个类别
   分数逐项相同,而且**三跑之间 baseline 文件 sha256 相同、pass1 答案
   2374/2374 逐字相同**。

3. **"复用缓存的 KV 本身会改答案"被否掉了。** 不挂 LMCache、只开 vLLM 自己的
   前缀缓存、同一批题跑两遍不清缓存:**0 / 2374 flip**,分数 1968.78 → 1968.78。
   且证明它真的复用了 —— pass B 的 prefill 快 **12.4 倍**(16 秒 → 1 秒,
   输入吞吐 79k → 982k tok/s),GPU KV 缓存 2,871,168 token 装得下整批。
   ~~"批次形状变导致数值抖动"也随之被否:vLLM 复用时批次形状同样变了。~~
   **【2026-08-26 晚,`10_` 推翻此推断的适用范围】这个对照的两遍都在"合批
   step"数值域里,它证明的是合批域内部稳定,证明不了跨域;而且原生冷跑时
   兄弟题当场复用(实测 cached=400/422),"复用"从未构成独立变量。**

4. ~~**所以位置锁在 LMCache 的存取往返本身**,机制未定。~~
   **【被 `10_` 推翻】KV 数值对比做了:注入 KV 与重算 KV 逐位相同(n=1 全层
   max_abs=0;并发下 15/18 翻转题逐位相同),且纯 vLLM、无 LMCache、pass2
   逐题提交时同样 18 题同方向复现。真机制:vLLM 0.27.1 首 token logits 在
   合批 step 与小 step 之间有确定性 ±1 bf16 量子差(±0.125),取回完成时序
   把 pass2 拖进小 step 域。LMCache 洗清。见 `10_`。**

5. **两个抽样模型对照 0.23,两个都至少红过一次:**

   | 模型 | 0.23 | 0.27.1 跑 1 | 0.27.1 跑 2 | 跑 3 |
   |---|---|---|---|---|
   | qwen2-vl-2b | flip **0**、hit 1.0 | 19 **FAIL** | 19 **FAIL** | 18 **FAIL** |
   | gemma-4-e4b | flip **0**、hit 0.9569 | 5 **PASS** | **15 FAIL** | — |

   chunk 16 与 chunk 32 都中,不是某一个粒度的事。
   **gemma 那次 PASS 是运气**:同模型同配置重跑一次就 15 个 flip、判红。
   这个模型的门结论**不可复现**(§四点十)。

6. **但两个模型的漂移形态不同,不能当成一种东西。**

   | | qwen2-vl-2b | gemma-4-e4b |
   |---|---|---|
   | 跑间 flip 集合 jaccard | **0.900 / 0.947 / 0.947** | **0.111** |
   | 交集 | 18(核心) | 2 |
   | flip 种类 | 全是 yes↔no | 跑 2 里 **13/15 有一头是空解析** |
   | parse ratio | 1.0 | 0.896 |

   qwen 是**确定性**偏差;gemma 主要是**非确定性**,而且集中在

## 二、为什么判"不是损坏"

MME 是 **1097 张图 × 每图 2 问**,同一张图的两问共享同一份图 KV。所以:

* **KV 被写坏** → 那张图的**两个问题一起翻**,而且分数单向掉。
  这是 gemma-4-e4b 在 0.23 上那次的形状:1288/2374 翻、分数掉 920.24,
  根因 `KEY_NOT_READABLE`(写锁 key 被当成命中)。
* **数值/批次非确定性** → 零散单题翻、双向翻、parse ratio 不变、类别有升有降。

实测:

| 判据 | qwen2-vl-2b | gemma-4-e4b | 损坏应有的样子 |
|---|---|---|---|
| flip 落在几张图 | 19 张 | 5 张 | 集中 |
| **同图两问共翻** | **0** | **0** | 高 |
| 方向 | 10 / 9 双向 | 双向 | 单向 |
| 类别 | 有升有降 | 有升有降 | 单向掉 |
| parse ratio | 1.0 | 0.896(与 0.23 同) | 掉 |
| 服务端 `KEY_NOT_READABLE` | **0 条** | **0 条** | 有 |

六条判据一致排除了"KV 被大面积写坏"。**当时我据此倾向"非确定性",这一步错了
—— 见 §四点八:判决实验显示漂移是确定性的。** 这六条排除的是粗粒度损坏,
排不掉"很小但确定的数值差异",而后者才是实测结果。

判据本身已工具化:`parity0271/flipstat.py`,给一个或多个 report 就打出方向、
同图共翻计数、空解析数、flip 索引,给两个还打集合重叠度与 jaccard。

## 三、`hit_coverage > 1` 已定性:是分母的建模保守,不是多复用了 KV

写这篇时先记成"待判",随后读代码 + 算已有数就定掉了,不需要再跑。

`coverage = pass2_external_cached_tokens / pass2_achievable_hit_tokens`,分母是

```python
achievable_hit_tokens = sum(g * ((t - 1) // g) for t in lookup_request_tokens)
```

那个 `-1` 是为"LMCache 从不返回 prompt 的最后一个 token"设的。但当 `t` 恰好是
`g` 的整数倍时,`(t-1)//g` 比 `t//g` 少 1,分母就**整整少一个 chunk**;`t` 不对齐
时两者相同。所以分母是个偏小的**模型值**,不是实测上限。

两跑的实测排序完全一致,而且是决定性的:

| | qwen2-vl-2b (g=16) | gemma-4-e4b (g=32) |
|---|---|---|
| `pass1_stored` | 1271680 | 668224 |
| `pass2_external_cached`(coverage 的分子) | 1268288 | 660800 |
| `pass2_achievable`(分母) | 1266912 | 655808 |
| `pass2_local_cached`(vLLM 自己前缀缓存的贡献) | **0** | **0** |
| 排序 | achievable < loaded **< stored** | achievable < loaded **< stored** |
| loaded − achievable | 1376 = **86** chunk | 4992 = **156** chunk |
| stored − loaded | 3392 = 212 chunk | 7424 = 232 chunk |

**`loaded < stored` 两跑都成立**,而且 `pass2_local_cached = 0`(没有一个 token
来自 vLLM 自己的前缀缓存,全部走连接器)。所以"pass2 复用的前缀比 pass1 存的长"
这个候选**被已有数据直接否掉**:pass2 装回来的比存进去的**少** 212 / 232 个 chunk。

`coverage` 越过 1 纯粹因为分母比真实存量小(小 298 / 388 个 chunk)。那 86 / 156
个 chunk 的超出量,是 prompt 长度**恰好对齐 chunk** 的请求数下界 —— 图像 token 数
量化过,对齐是常态。

两条推论:

* **它解释不了 flip**,这是计数问题不是内容问题,§二 那条线索到此断了;
* **它也不会误判门**:`min_hit_coverage` 是 0.95 的下限,超过 1 永远不会红。
  真正该改的是那个指标的可读性(打出 >1 会让人误读),不是算法。低优先级。

## 四点九、不含 LMCache 的对照:vLLM 自己的前缀缓存**一题都不翻**

`vllm_prefix_drift.py`(已归档),同一个引擎、`enable_prefix_caching=True`、
两遍之间**不清缓存**,全程不加载 LMCache:

```
flips(B vs A) = 0 / 2374
score pass_a 1968.78 -> pass_b 1968.78
unparseable 0 / 0
```

**先证这个对照是有效的**,否则"0 flip"可能只是缓存被清空后重算了一遍:

* pass A:2374 题 **16 秒**,输入吞吐 **79,122 tok/s**;
* pass B:2374 题 **1 秒**,输入吞吐 **981,696 tok/s** —— **12.4 倍**。
  只有 prefill 被跳过才可能;
* `GPU KV cache size: 2,871,168 tokens`,而本工作负载的 lookup 总量约 1.29 M,
  **整批都装得下**,两遍之间没有驱逐。

所以 pass B 确实是**从 vLLM 自己的前缀缓存服务的,而它一个答案都没改**。

| **LMCache 复用缓存的 KV** | **确定性翻 18 题** | 三跑交集 18 / 并集 20 |

### 核心 18 题落在哪些类别(用已有数据白算,不用再跑)

D 跑翻的正好是核心 18 题,所以它的逐类别差就是核心自己的:

```
numerical_calculation  72.50 -> 65.00   (-7.50)
text_translation      185.00 -> 177.50  (-7.50)
color                 180.00 -> 185.00  (+5.00)
landmark              175.25 -> 176.00  (+0.75)
artwork               141.00 -> 140.50  (-0.50)
perception 1523.78 -> 1529.03   cognition 445.0 -> 430.0
```

**横跨 5 / 14 个类别,perception 与 cognition 都有,方向有升有降。** 所以这不是
某一类内容特有的缺陷(不是只影响 OCR / 文本之类),符合"一个很小的数值差异把
恰好在边界上的题推过去"这个形状,与题目内容无关。

顺带对上了账:B 比 D 多翻 #58,而 B 的 artwork 比 D 高 0.75 → #58 是 artwork 题;
C 比 D 多翻 #24,而 C 的 code_reasoning 比 D 高 7.50 → #24 是 code_reasoning 题。
两跑的差值能逐项对上,说明这三份报告内部自洽。

## 四点十、gemma-4-e4b 重跑:5 → 15,那次绿是运气

| | 跑 1 | 跑 2 |
|---|---|---|
| baseline sha256 | `a145a0f341f8302d` | **同一个**,2374/2374 逐字相同 |
| **pass1 逐字相同** | — | **2374/2374** |
| pass2 逐字相同 | — | 2326/2374(48 处原始差异) |
| pass2 语义 flip | **5** | **15** |
| 门 | **PASS** | **FAIL** |
| score_delta | 4.25 | **1.09**(方向还反了:pass2 比 pass1 高) |
| flip 索引 | 889 1244 1326 1414 2298 | 185 235 278 299 364 392 447 474 490 533 628 633 1326 1472 2298 |
| 两跑交集 | **2**(1326、2298),jaccard **0.111** | |

两条结论:

1. **gemma 的门结论不可复现。** 5 个过、15 个不过,预算 11.87 正好卡在中间。
   所以"gemma-4-e4b 在 0.27.1 上 parity 绿"**不能说**;能说的是"跑两次,一次
   过一次不过"。
2. **gemma 的漂移主要是非确定性的**,与 qwen 不同(jaccard 0.111 对 0.900+),
   而且**集中在截断边界**:跑 2 的 15 个里 **13 个有一头是空解析**
   (`''→no` 6、`no→''` 7)。这个模型 `max_tokens=8`,约 10% 的答案本来就
   解析不出(parse ratio 0.896),所以一点数值差异就能让判决落进或落出那 8 个
   token —— 这测的是解码预算的边缘度,不是答案被改坏。

**这给门的设计提了一个问题**:`''` 与 `yes`/`no` 之间的翻转,和 `yes`↔`no` 的
翻转,现在按同一个 flip 计数。对会弃答的模型,前者衡量的是截断边缘度。要不要
分开计,是一个独立的决定,本篇只记下依据。

## 五、这回答了 8-26 最初那个问题

用户问的是"在这个版本的 vllm,MP 模式的 LMCache 对模型的支持程度是不是基本回到了
0.23 的状态"。现在有数了:**不是。**

0.23 的 SUPPORTED 定义是"合成套件 + MME parity 双绿"。抽查的两个模型:

* 合成套件:5/5 全绿(`7_`),这一半确实回来了;
* MME parity:两个模型的 hit 路径都从"逐字一致"退到"不一致",而且**两个都
  至少红过一次**(qwen 三跑三红;gemma 一过一红,门结论不可复现)。
  **这一半没回来,而且不能出证** —— 不是"证书还没生成",是生成了也会是
  NOT_SUPPORTED。

可以说的:"**vLLM 0.27.1 上 MP 模式的合成套件已全绿(抽 5 个模型 140 用例),
但全量 MME parity 抽查的两个模型都过不了门:qwen2-vl-2b 三跑 19/19/18 flip,
其中 18 个是三跑共有的确定性核心;gemma-4-e4b 两跑 5(过)与 15(不过),
门结论不可复现。存路径仍逐字节精确(pass1 对 plain vLLM 零偏差,答案跨跑
逐字相同)。'复用缓存的 KV 本身会改答案'已被不含 LMCache 的对照否掉
(只开 vLLM 自己的前缀缓存跑两遍,0/2374 flip,而 pass B 的 prefill 快 12.4 倍
证明确实复用)。~~所以偏差的位置在 LMCache 的存取往返,机制未定。~~**"

**【2026-08-26 晚更新】上句结尾已过时:机制当天闭合(`10_`),LMCache 存取
逐位保真,翻转是 vLLM 0.27.1 合批/小 step 两个数值域的 ±1 bf16 量子差,纯
vLLM 无 LMCache 可复现同样 18 题。可引用的最终版本见 `10_` 结论先写。
