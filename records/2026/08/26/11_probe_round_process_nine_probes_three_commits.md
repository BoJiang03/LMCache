## 二、过程里的事故与教训

1. **探针本身摔了四次才跑通**,每次都是环境事实与假设不符:
   - KV 布局假设 `(2, blocks, ...)`,实际 qwen2-vl 是 `(blocks, 2, 16, 256)`(块维在 0);
   - `op.token_ids` 是张量,与 int 列表 `==` 恒 False;
   - LMCache 把图像占位 token 重写为 mm-hash 衍生 id,**op.token_ids 与 prompt_token_ids 不可直接匹配**——改用请求 id 前导序号映射;
   - 请求 id 格式是 `0-85233d2c`(前导序号-随机后缀),不是尾缀序号。
2. **pass 结束后的 KV 快照不可靠**:vLLM 会回收已释放块,`mixed` 探针里
   3 题(299/741/823)的"大差异"读数(max_abs≈19、整块级)就是这么来的。
   正确做法是在 store op 提交点抓(该请求的块还被 delay-free 持着)。
   这 3 题差点把"注入损坏"的错误结论送回来——靠 15/18 为 0 diff +
   差异形态(内容级而非量子级)拦住了。
3. **GPU 被别的 session 拿走不是事故,是常态**:mixed 探针第一跑摔在
   GPU 2 只剩 52 GiB——`vllm-lazy` venv 的另一 session(pgid 417410)
   四分钟前拿了 GPU 0/2/3/5。按 venv+pgid 判归属后换 GPU 1,没动别人的进程。
4. **对照实验要核对它真的对照了目标变量**:`8_` 的 drift 对照两遍都在
   合批域,它"否掉批形状漂移"否的是错误的对象。这次的教训写法:
   排除法列表里每一项都要问"我的对照真的踩进了那个条件吗"——
   `native241` 的 cached=400/422 一个数字就把旧前提掀了。
5. **±0.125 的整齐是指纹**:47 个 gap 移动全是恰好一个 bf16 量子,
   没有一例其他幅度。损坏是任意幅度的,数值路径差是量子化的——
   这个区分本可以更早把"损坏"假设的优先级压下去。
6. **110 题子集是本轮最划算的投资**:13 分钟抽取一次,之后每个假设
   7 分钟检验(全量跑 45-55 分钟)。翻转集合跨规模逐题稳定,
   使小规模检验有效。
